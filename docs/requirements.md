# 即时通讯软件需求说明书（第一阶段）

## 1 项目概述

本项目是一款面向 Web 端的即时通讯软件。第一阶段要打通"账号 → 好友 → 一对一文字聊天"的完整流程，并保证消息不丢、不重、有序，聊天记录可以追溯。项目分阶段迭代，后续功能在本阶段的架构上扩展。

**本阶段包含：** 注册、登录、退出；好友搜索、申请、处理、删除；文字单聊（含实时和离线）；会话列表与未读数；历史记录分页加载与本地缓存；消息逐条删除（仅对自己生效）。

**本阶段不包含：** 群聊；图片、文件、语音消息；音视频通话；消息撤回；已读回执；移动端和桌面端客户端。

## 2 功能需求

本阶段共 21 条功能需求，按模块编号，便于后续开发和测试逐条对照。

### 2.1 账号

- **FR-01 注册：** 使用"用户名 + 密码"注册。用户名允许重复（大小写不同也视为可重复），账号由系统随机分配的 10 位数字用户 ID 唯一标识（任意两个账号的 ID 都不相同），注册成功后返回用户 ID。用户名同时作为昵称展示，不单独设置昵称。用户名为 3-32 位英文字母或数字；密码为 8-24 位可打印 ASCII 字符（不含空格），至少包含一个大写字母、一个小写字母和一个数字。
- **FR-02 登录：** 使用"用户 ID + 密码"登录，登录成功后服务端签发访问令牌（JWT），有效期 3 天，过期后需重新登录。用户不存在和密码错误返回相同的提示。之后的 HTTP 请求和 WebSocket 建连都必须携带该令牌。
- **FR-03 退出：** 清除前端保存的令牌，并断开长连接；同时删除该用户在本浏览器的本地缓存（IndexedDB），下次登录时按需从服务端重新拉取。令牌过期导致的被动登出不删除缓存。
- **FR-04 多处登录：** 同一账号允许在多个浏览器标签页或设备上同时在线，新消息推送到该账号的所有在线连接。自己在某一处发出的消息、好友操作，也同步到自己的其他在线连接。

### 2.2 好友

- **FR-05 搜索：** 按用户名或用户 ID 搜索用户。用户名为完全匹配、不区分大小写；输入为 10 位数字时同时按用户 ID 精确匹配（纯数字用户名也合法，两种结果合并去重）。用户名可能重名，搜索结果需同时显示用户 ID 以便区分。结果不包含自己，最多 20 条，每条标明与自己的关系（可添加 / 已是好友 / 已申请 / 对方已申请我）。
- **FR-06 发送申请：** 向对方发送好友申请，可附带一条验证信息（最多 100 个字符）。不能添加自己；已是好友时不能申请。两人之间（不分方向）最多存在一条待处理申请：A 对 B 已有待处理申请时，A 再次申请直接返回已有申请，不重复创建；B 不能再向 A 发送申请，只能处理 A 的申请。申请被拒绝后可以重新申请。
- **FR-07 处理申请：** 被申请方可以同意或拒绝，同意后双方成为好友；只能处理发给自己的、尚未处理的申请。收到新申请时通知被申请方，申请被同意或拒绝时通知申请方：在线时通过 WebSocket 实时通知；离线时，下次登录可在"收到的申请"或"我发出的申请"列表中看到。
- **FR-08 删除好友：** 删除后双方解除好友关系（双向解除），不通知对方。聊天记录保留，仍可查看历史。之后再发消息按非好友处理（见 FR-12）。重新加好友需要再次申请。
- **FR-09 好友页：** 好友页与聊天页分开。好友页显示好友列表（按用户名排序，显示用户名和用户 ID）、收到的待处理申请和我发出的申请，在好友详情中点击"发消息"进入与其的对话框。

### 2.3 单聊消息

- **FR-10 实时收发：** 支持文字消息。接收方在线时实时推送；离线时消息先存储，上线后拉取（离线消息）。
- **FR-11 可靠性：** 客户端为每条消息生成唯一 ID；服务端写库成功后回复确认（ACK）。客户端超时未收到 ACK 就重发，服务端按该 ID 去重。每个会话内的消息带有递增序号 seq，用来保证顺序。
- **FR-12 非好友限制：** 非好友之间，在对方回复或双方成为好友之前，发送方最多只能发一条消息；超出时服务端拒绝并返回明确的错误码。（M6 实现；M4、M5 阶段非好友之间一律不能发送，返回 40003。）
- **FR-13 内容限制：** 单条消息不能为空（不能全是空白），最多 1500 个字符（按 Unicode 字符计数，中文、emoji 都算 1 个）。超出上限的消息不发送到服务端，在发送方本地显示为一条发送失败的消息（带红色叉号），提示"消息过长，请重新发送"；这条消息只有发送方自己能看到，不写入服务器。服务端同样校验上限，超出时返回错误码 40002。

### 2.4 会话列表（聊天页）

- **FR-14 会话列表：** 聊天页左侧只列出有消息的会话，按最后一条消息的时间倒序；每项显示对方头像和用户名、最后一条消息摘要、时间和未读数（超过 99 显示 99+）。
  - 从好友页进入一个还没有消息的会话时，在列表顶部临时显示这一项，不保存；离开后没有发出消息就消失。
  - 收到新消息时，对应会话移到最前；会话不在列表中时，从服务端重新拉取列表。
  - 已解除好友关系的会话仍保留在列表中，可以查看历史，但不能发送（FR-12 实现前）。
  - 左侧导航"聊天"图标显示所有会话的未读总数。
  - 不提供从列表中删除或隐藏会话的功能。
- **FR-15 未读与已读：** 服务端为每个用户在每个会话中记录已读位置 read_seq，未读数 = last_seq − read_seq。read_seq 只增不减，按以下规则推进：
  1. **实际看到才算已读：** 页面可见时，一条消息的底边进入消息区可视范围，才算看到这条消息。read_seq 只连续推进到"中间没有未看到的消息"的最大 seq，跳着看到的靠后消息不能让它越过前面没看到的消息；自己发的消息在推进时直接跳过。打开对话框本身不改变已读状态。
  2. **发送即已读：** 发送消息时，发送方的 read_seq 推进到这条消息的 seq。用户没有回看就发送了新消息，视为已读完之前的新消息。
  3. **标记为已读：** 用户点击"标记为已读"时，read_seq 推进到客户端此刻已知的最新 seq。
  - **打开会话时的交互（参照 Discord）：** 对话框停在最新一页，在第一条未读消息上方插入"以下为新消息"分隔线，离开会话前保留。未读消息全部在可视范围内时无需额外操作；否则顶部显示"N 条新消息"横条，提供"跳转"和"标记为已读"。跳转时定位到第一条未读消息（不在本地时从它开始向服务端拉取，向下滚动继续加载，直到与最新消息接上），并在底部提供"跳到最新"。
  - **停留在会话中：** 用户向上翻看历史时，新到的消息不算已读，底部提示"N 条新消息 ↓"。
  - **多处登录：** 已读变化同步到自己的其他在线连接，保证多处未读数一致。本阶段不做已读回执，read_seq 不推送给对方。

### 2.5 历史记录与本地缓存

- **FR-16 本地缓存：** 使用浏览器 IndexedDB（Dexie），每个用户一个独立的库。缓存三类数据：
  - 已确认的消息；
  - 会话列表快照（打开页面时先显示快照，再用服务端结果刷新）；
  - 本地未确认的消息（发送中、发送失败、超长）：刷新页面后显示为"发送失败，点击重试"，重试沿用原 clientMsgId。
  同一用户的多个标签页共用一个库，写入按消息唯一键覆盖，保证幂等。退出登录时删除该库（见 FR-03）。
- **FR-17 增量同步：** 登录和断线重连后刷新会话列表，未打开过的会话也能看到离线期间的新消息和未读数（即离线拉取）。打开会话或重连时，打开着的会话以本地已同步的最大 seq 为起点，向服务端请求更新的消息。本地落后服务端超过一页时只拉取最新一页，中间留下缺口，等用户向上翻到缺口时再补。客户端用"已同步的 seq 区间"判断缺口，不依赖 seq 是否连续（M6 删除消息后，客户端看到的 seq 本来就不连续）。
- **FR-18 分页拉取：** 首次登录或清除本地缓存后，只加载最近一页消息。用户滚动到顶部时自动加载更早的消息：已同步区间内的从本地缓存读取，遇到缺口或超出本地范围时，按 seq 向服务端分页拉取，不一次性拉取全部记录。

### 2.6 删除

- **FR-19 逐条删除：** 用户可以删除单条消息，只对自己生效，对方仍能看到。不提供一键清除全部聊天记录的功能。
- **FR-20 删除的实现方式：** 服务端记录"某用户删除了某条消息"，该用户拉取历史时过滤掉这些消息。这样清除缓存或换设备后，已删除的消息不会重新出现。
- **FR-21 服务端数据不清除：** 删除消息、删除好友等任何操作都不物理删除服务端的消息数据。（删除好友时物理删除的是 friendships 中的关系记录，不涉及消息数据。）

## 3 非功能需求

"高可扩展、高可维护"落实为下面可以检查的设计约束。第一阶段以功能正确为主，不设性能指标，压测放到后续阶段。

### 3.1 安全

- **NFR-01 密码：** 只存 bcrypt 哈希，不存明文，密码不写入日志。
- **NFR-02 鉴权：** 除注册和登录外，所有接口都要校验令牌；WebSocket 在建立连接时校验。发送方身份一律取自令牌，不信任客户端传来的用户 ID。
- **NFR-03 数据权限：** 用户只能读取自己参与的会话中的消息。
- **NFR-04 消息内容只作为数据：** 消息内容一律按纯文本处理，不会被服务端解析或执行。数据库访问全部使用参数化查询，防止 SQL 注入；前端渲染时转义（不使用 `dangerouslySetInnerHTML`），防止 XSS。
- **NFR-05 限流：** 注册、登录、好友申请、发消息等接口按用户或 IP 限制频率。
- **NFR-06 传输加密：** 部署到公网时使用 HTTPS 和 WSS。

### 3.2 可扩展性

- **NFR-07 模块化单体：** 初期只部署一个 Go 服务，内部按用户、好友、消息、长连接网关划分模块，模块之间只通过接口调用。以后需要拆分服务时，按模块边界拆。
- **NFR-08 网关与业务分离：** 网关只负责连接管理、心跳和数据包收发，不写业务逻辑。以后网关部署多台时，业务代码不用改。
- **NFR-09 协议可扩展：** WebSocket 数据包统一带 `type` 和 `version` 字段，新增消息类型时不影响已有处理逻辑。
- **NFR-10 预留 Redis：** 在线状态和"用户连在哪个网关实例上"先定义成接口，第一阶段用内存实现，后续换成 Redis 实现。

### 3.3 可维护性

- **NFR-11 分层：** 每个模块内部分为 handler（接口层）、service（业务层）、repository（数据访问层）。
- **NFR-12 数据库变更：** 表结构的任何变更都通过迁移脚本完成，不手动改表。
- **NFR-13 统一规范：** 统一错误码、结构化日志（记录请求 ID 和用户 ID），配置通过配置文件和环境变量注入。
- **NFR-14 测试：** 消息可靠性相关的关键路径（ACK、去重、seq、断线重连）必须有自动化测试覆盖。

## 4 运行环境与技术选型

初版只做 Web 网页端：前端用 React + TypeScript + Vite，后端用 Go，数据库用 PostgreSQL。本地开发通过 Docker Compose 启动依赖服务。

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 后端语言 | Go | goroutine 很轻量，一个连接对应一两个 goroutine 就能支撑大量长连接；编译后是单个可执行文件，部署简单；是目前即时通讯后端的主流语言之一 |
| HTTP 框架 | Gin | 资料和中间件最多，鉴权、限流、日志都有现成方案 |
| 长连接 | gorilla/websocket | 使用最广的 Go WebSocket 库，示例充足 |
| 数据库 | PostgreSQL | 事务和数据一致性可靠；支持 JSONB，消息结构变复杂后比较灵活；完全开源 |
| 数据库访问 | GORM | 上手快，默认参数化查询；复杂查询可以直接写 SQL |
| 数据库迁移 | golang-migrate | 表结构变更有版本号，可以升级和回滚 |
| 缓存 / 在线状态 | Redis + go-redis | 第一阶段不用，架构上预留接口（见 NFR-10） |
| 鉴权 | JWT | 无状态，HTTP 和 WebSocket 共用一套校验 |
| 密码存储 | bcrypt | 自带加盐，计算成本可调，抗暴力破解 |
| 日志 | 标准库 slog | 标准库自带结构化日志，不引入第三方依赖 |
| 前端框架 | React + TypeScript + Vite | 类型检查减少协议字段写错；开发热更新快 |
| 状态管理 / 路由 / UI | Zustand / React Router / Ant Design | Zustand 轻量，适合保存会话和连接状态；Ant Design 组件齐全，有中文文档 |
| 前端本地缓存 | IndexedDB（用 Dexie.js 封装） | 浏览器内的本地数据库，容量大，支持按会话和 seq 建索引；Dexie 简化了原生 API（对应 FR-16） |
| 本地环境 | Docker Compose | 一条命令启动 PostgreSQL（以及后续的 Redis） |

## 5 总体架构

系统分为浏览器、Go 服务、存储三层。

- **浏览器：** React 前端负责页面、状态管理和协议收发；IndexedDB 按用户隔离，缓存已收到的消息。
- **Go 服务（模块化单体）：** 入口有两个——HTTP 接口（Gin）负责注册登录、好友操作、历史拉取等"请求-响应"类操作；WebSocket 网关只负责鉴权建连、心跳和数据包收发。业务逻辑分在用户模块、好友模块、消息模块中，网关收到的消息交给消息模块处理。
- **存储：** PostgreSQL 保存用户、好友、会话、消息、删除记录；Redis 为后续阶段预留，用于在线状态和多实例连接路由。

### 5.1 一条消息的发送流程

1. 发送方前端生成 client_msg_id，先在界面上显示为"发送中"，再通过 WebSocket 发出。
2. 网关根据建连时已校验的身份确定发送方，把消息交给消息模块。
3. 消息模块检查好友关系和非好友限制（FR-12），再按 client_msg_id 去重：重复消息直接返回已有的 seq；新消息在事务中分配 seq 并写入 PostgreSQL，同时把发送方的 read_seq 推进到这个 seq（FR-15）。发送方的其他连接收到自己发的 `message.new` 时，在本地同样推进 read_seq，不需要额外推送。
4. 写库成功后，服务端向发送方回复 ACK（带 seq）。前端改为"已发送"并写入 IndexedDB；超时未收到 ACK 时，用同一个 client_msg_id 重发。
5. 消息模块把消息推送到接收方的所有在线连接。接收方写入 IndexedDB，如果发现 seq 不连续，就主动拉取缺失的消息。
6. 接收方离线时不推送，下次上线时按本地最大 seq 拉取，即离线消息。

## 6 数据模型（初步）

第一阶段共 7 张表（message_deletions 在 M6 创建）。消息永不物理删除，"删除"和"已读"都单独建表记录。

| 表 | 主要字段 | 说明 |
| --- | --- | --- |
| users | id、username、password_hash、avatar_url、created_at | id 为随机 10 位数（主键，CHECK 限定范围），唯一标识账号；username 不唯一，兼作昵称，建 lower(username) 普通索引用于搜索 |
| friend_requests | id、from_user_id、to_user_id、message、status、created_at、handled_at | status 取值 pending / accepted / rejected；message 最多 100 字符；部分唯一索引 (LEAST(from,to), GREATEST(from,to)) WHERE status = 'pending' 保证两人之间最多一条待处理申请；处理后的记录保留 |
| friendships | user_id、friend_id、created_at | 双向各存一条，主键 (user_id, friend_id)；删除好友时两条一起删 |
| conversations | id、user_a、user_b、last_seq、last_message_at、created_at | 一对用户只有一个单聊会话；user_a 存较小的用户 ID，(user_a, user_b) 唯一；还没有消息时 last_message_at 为 NULL，会话列表只返回 last_seq > 0 的会话 |
| conversation_members | conversation_id、user_id、read_seq | read_seq 为该用户已读到的 seq，推进规则见 FR-15；未读数 = last_seq − read_seq；以后群聊可直接复用 |
| messages | id、conversation_id、seq、sender_id、client_msg_id、type、content、created_at | (conversation_id, seq) 唯一，用于排序和分页；(sender_id, client_msg_id) 唯一，用于去重 |
| message_deletions | user_id、message_id、deleted_at | 主键 (user_id, message_id)；拉取历史时过滤（FR-20） |

seq 的分配与消息写入放在同一个事务里：先执行 `UPDATE conversations SET last_seq = last_seq + 1 WHERE id = ? RETURNING last_seq` 拿到新的 seq，再插入消息。这样同一会话并发发送时 seq 不会重复。

## 7 开发计划

按 6 个里程碑依次推进，每个里程碑达到完成标准后再进入下一个。

| 里程碑 | 内容 | 完成标准 |
| --- | --- | --- |
| M1 项目骨架 | 前后端工程、Docker Compose、迁移脚本、统一错误码和日志 | 一条命令启动全部服务，健康检查接口返回正常 |
| M2 账号 | 注册、登录、退出、JWT 鉴权中间件 | 未登录访问受保护接口返回 401 |
| M3 好友 | 搜索、申请、同意或拒绝、删除、好友页（实时通知在 M4 接入） | 两个账号互加好友、再删除的流程全部走通 |
| M4 实时单聊 | WebSocket 建连鉴权、心跳、收发、ACK、去重、seq | 制造断网重连和重复发送后，消息不丢、不重、不乱序 |
| M5 会话与历史 | 会话列表、未读数、离线拉取、分页、IndexedDB 缓存 | 清除缓存后重新登录，历史可以按需分页恢复；离线期间收到的消息，登录后在会话列表中显示为未读；未读需实际看到、发送消息或标记已读才清零，多个标签页之间未读数一致 |
| M6 删除与限制 | 逐条删除、非好友消息限制、接口限流 | 删除的消息换一个浏览器登录后仍不出现 |
